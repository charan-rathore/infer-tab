# One persistent inference machine

## Architecture decision

The original UI used three component-local state machines, reset the playhead on
policy changes, exposed terminology before discovery, and recalculated Experiment
03 with a fixed head width. Keep the correct Python experiments. Add a thin shared
interaction system over their immutable recordings.

Data flows in one direction: Python trace → validated adapter → deterministic
interaction reducer → visual projection. No animation callbacks, timers, or effects
may supply counts, generated tokens, equivalence, or discovery completion.

Primitives: semantic learner events, bounded playhead, prediction commitments,
stable position IDs, trace field references, contextual selection, shared work and
shelf view, progressive derivations, and versioned portable replay files. The event
vocabulary is an analytics seam; there is no telemetry transport or analytics store.

## Discovery contract

| State | 01 Repeating work | 02 Read vs write | 03 Math vs data |
| --- | --- | --- | --- |
| First interaction | Build the first word | Inspect the first question | Count the single query's math |
| Prediction | How many rows will the next step build? | May the first question read a later word? | Will smaller numbers reduce arithmetic, bytes, or both? |
| Failure | Old positions are rebuilt | The attempted future read is blocked | A small arithmetic count still requires the long shelf |
| Mechanism | Keep completed rows | Process existing prompt queries together, preserving the causal mask | Halve symbolic element width |
| Aha | One new row, old rows reused, equivalent output | Many valid prompt queries, then one new query | Same arithmetic, half the logical payload |
| Derivation | Sum actual observed projection counts | Recorded square, usable triangle, and row counts | Recorded arithmetic divided by recorded Q + K + V bytes |
| Term | KV cache | Prefill and decode | Arithmetic intensity |
| Next bottleneck | Reuse still reads the shelf | A single query still needs the whole shelf | Hardware throughput and actual traffic are needed to establish a bottleneck |

Experiment 02's blocked read is a causal constraint, not a defect corrected by
parallelism. Parallel prompt processing retains that restriction; the serial view
is an explanatory inspection of a recorded parallel pass, not a benchmark.

## Identity and provenance

Token vocabulary IDs are not object IDs: repeated words occupy distinct positions.
Semantic IDs include the exact prompt sequence and position; tensor identities also
include their trace source. Policy changes preserve positions and the playhead.
The root provider preserves selections and lesson progress across route changes.
Length changes select recorded scenarios; they do not invent generated tokens.

01 uses a 128-position table, while 02 uses 256 positions, changing seeded weights.
Never claim their K/V tensors or generated outputs are identical. The additional
six-token arithmetic fixture is generated by existing Experiment 03 Python logic,
which calls Experiment 02's run_pair, aligning the default 02/03 shapes and prompt.
Custom 01 prompts remain local recordings; subsequent lenses explicitly show their
own source scenario rather than relabeling tensors as belonging to the custom run.

## Ownership and replay

Python owns tokenization, weights, tensor values, outputs, numerical equivalence,
shapes, row counts, symbolic FLOPs, logical bytes, dtype comparisons, and measurement
caveats. Adapters select records and sum observed quantities; they never run a model.
Visual state owns the lesson stage, selection, depth, and playhead. A policy switch
is a counterfactual replay from the same prompt, not a mid-run cache warm-up.

Example events: prediction.committed {lesson: '01', answer: 'one'};
mechanism.changed {lesson: '01'}. The latter selects the cached recording at the
same playhead. Discovery stages are explicit and ordered. Repeated/invalid events
cannot skip a required prediction. Replay stores the trace bundle and bounded event
history so custom runs do not depend on Python rerunning identically on another PC.

## Delivery and traps

Build adapters/reducer and invariants first; complete 01; connect 02/03; add portable
replay and inspection; verify trace accounting, interaction paths, and browser use.
Document every new function. Avoid a general simulation engine, analytics backend,
decorative motion, fabricated hardware timing, or formulas that overwrite traces.
